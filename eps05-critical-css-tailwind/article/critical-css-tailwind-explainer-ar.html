🎬 الحلقة ٥

هل Tailwind CSS يغني عن Critical CSS؟

مرة كل الـ Utility Classes بتتولد في ملف output.css واحد بعد الـ Build، الناس بتفتكر إن Tailwind "بيحل" مشكلة CSS الكبير أوتوماتيك. بس هل ده معناه إنك مش محتاج Critical CSS تاني؟ خلينا نشوف الأرقام.

🧠 إيه اللي اتغيّر مع Tailwind؟

Utility-first مش معناها "مفيش Render-blocking"

Tailwind وقت الـ Build بياخد كل الـ Classes اللي فعلًا مستخدمة في الـ HTML، وبيولّد منها ملف CSS واحد Purged — يعني من غير أي Class إنت مش مستخدمها. الملف ده بيبقى أصغر بكتير من لو كتبت CSS تقليدي، لكنه برضو:

HTML + Tailwind classes
→
Tailwind Build توليد CSS
→
Purged CSS ملف واحد خارجي
→
Paint 🎨
⚠️
لسه عندك <link rel="stylesheet" href="output.css"> — يعني لسه فيه Network Request واحد Render-blocking قبل ما المتصفح يرسم أي حاجة. حجم الملف اتقلل، بس طبيعته لسه هي هي: المتصفح مش هيرسم قبل ما يوصله ويحلّله.
🧪 التجربة

Before / After بنفس الـ 10s Delay

استخدمت نفس السيرفر اللي عملته في التجارب اللي فاتت — server.js بيأخر أي Request لـ output.css بمقدار 10 ثواني عشان يحاكي شبكة بطيئة، وده بيوريك بالظبط إمتى الصفحة بتتلون.

🔍 النقطة اللي هتلفت نظرك

ليه الـ LCP لسه ~10.1s حتى بعد Critical CSS؟

ده أهم رقم في التجربة كلها. لاحظ إن First Paint اتحسّن من 10 ثواني لـ 7 ميلي ثانية — ده لأن critical.css بقى Inline في الـ <head>، فالمتصفح رسم الـ Hero والـ Header فورًا. لكن Largest Paint فضل واقف عند ~10.1s.

<!-- ده اللي فرق في نسخة After --> <head> <!-- Critical CSS: Inline, بيرسم فورًا --> <link rel="stylesheet" href="critical.css" > <!-- Tailwind الكامل: لسه بياخد وقته --> <link rel="stylesheet" href="output.css" > </head>
💡
الـ critical.css عندك بيغطي الـ Header والـ Hero بس (نصوص، أزرار، Browser mockup). لكن أكبر عنصر بصري في الصفحة — الـ Grid بتاع الـ Metrics تحت — Classes بتاعته (زي grid-cols-4 وrounded-lg) مش موجودة في الـ Critical subset، فبيفضل مستني الـ output.css الكامل يوصل عشان يتلوّن صح. يعني Critical CSS حسّن الـ FCP بشكل جامد، لكن مسحش المشكلة، بس نقلها لمكان تاني.

يعني الإجابة على سؤال العنوان: لأ، Tailwind لوحده مش بديل عن Critical CSS. هو بيقلل حجم المشكلة (Purging)، لكن لسه بيبعت ملف CSS واحد Render-blocking. Critical CSS لسه له دور — يحسّن أول ظهور (FCP) — لكن لازم تنتبه إن الـ Critical subset بتاعك يغطي فعلًا كل حاجة above-the-fold، وإلا هتحسّن FCP وتسيب LCP لوحده يتعطل.

🛠️ التطبيق العملي

إزاي تطبّق Critical CSS مع Tailwind فعليًا؟

الفكرة واحدة سواء بتشتغل بـ HTML عادي أو React: تستخرج الـ Rules اللي بتغطي أول شاشة (Above-the-fold) من ملف output.css بتاع Tailwind، وتحطها Inline جوه <head>، وتسيب الباقي يتحمّل عادي بـ <link> من غير ما يمنع الرسم.

1) HTML عادي — باستخدام critical

بعد ما Tailwind يعمل Build ويطلّع output.css الـ Purged، شغّل أداة زي critical على الصفحة النهائية عشان تولّد نسخة فيها الـ Critical subset Inline:

// npm i -D critical // generate-critical.js import { generate } from "critical"; await generate({ base: "dist/", // فولدر الـ Build src: "index.html", target: "index.html", // بيكتب فوق نفس الملف Inline css: ["dist/output.css"], // ناتج Tailwind inline: true, width: 1300, height: 900, });
💡
الأداة بتفتح الصفحة فعليًا (Headless Chrome) وبتشوف أنهي Classes اتلونت فعلًا في أول Viewport، وبتحطها Inline — يعني مش لازم تكتب critical.css بإيدك زي المثال اللي فوق.
2) React — مع Vite

في مشروع React مبني بـ Vite، ممكن تشغّل نفس الفكرة كـ Plugin وقت الـ Build، فكل صفحة طالعة من vite build بتاخد نسخة Inline أوتوماتيك:

// npm i -D vite-plugin-critical // vite.config.js import { defineConfig } from "vite"; import critical from "vite-plugin-critical"; export default defineConfig({ plugins: [ critical({ criticalBase: "./dist/", criticalPages: [{ uri: "", template: "index" }], criticalConfig: { inline: true, extract: false }, }), ], });
⚠️
في React، الـ Classes اللي بتتبني Dynamic (زي `bg-${color}-500`) ممكن Tailwind الأساسي يعملها Purge غلط، وده بينعكس على الـ Critical extraction كمان. الحل: اكتب الـ Class كاملة صريحة، أو ضيفها في safelist جوه tailwind.config.js.
3) Next.js — الطريق الأسهل عمليًا

لو بتستخدم Next.js، الأداتين اللي فوق مش متكاملتين بشكل رسمي معاه. البديل الشائع هو beasties (الخلف الرسمي لمشروع Critters اللي بقى Deprecated) كـ Webpack Plugin في next.config.js، وهو نفس المبدأ: بيقرا الـ HTML الناتج ويحط الـ Critical CSS Inline تلقائي في كل صفحة وقت الـ Build.

🤔 نقاش مهم

طب يبقى Critical CSS بقى زيادة عن اللزوم مع Tailwind؟

في رأي منتشر إن أدوات الـ Critical CSS اتعملت أصلًا لملفات ضخمة (ميجابايتات)، وإن Tailwind بالـ Purge بتاعه بيخليها Overkill — بل ممكن تعمل مشاكل أكتر ما تحل. خلينا نشوف نقط الاتفاق ونقط اللي محتاجة تفصيل أكتر.

المشكلةالاعتراض على Critical CSS مع Tailwind
Diminishing Returnsالأداة اتعملت لملفات ضخمة؛ ملف Tailwind الـ Purged أصلًا صغير (10–15 KB) فمفيش حاجة كبيرة تتقسم
Cascade Order BugsTailwind بيعتمد على ترتيب Layers (Base → Components → Utilities)؛ تقسيم غلط ممكن يكسر hover: أو md:
Automation Overheadالـ Above-the-fold صعب تحدده في تطبيقات Dynamic؛ الأدوات ممكن تفوت Classes بتظهر بعد تفاعل المستخدم
✅
النقط دي صح فعلًا، خصوصًا إن أداة الـ Critical CSS بقت بتوفر جزء صغير جدًا من ملف أصلًا صغير — العائد بقى أقل بكتير من زمان.
البديل المطروح: Inline كل حاجة

الاقتراح إنك بدل ما تقسم الملف، تعمل Inline للـ output.css بالكامل جوه <head> — تلغي الـ Network Request خالص، وطالما الصفحة كلها (HTML + CSS) تحت ~14 KB مضغوطة، بتوصل في أول TCP Packet وترسم فورًا. النقطة دي صح تقنيًا — قاعدة الـ 14 KB حقيقية.

⚠️
لكن فيه نقطة بتتنسى: ملف CSS خارجي مربوط بـ <link>، حتى من غير أي Critical splitting، بيتحمّل مرة واحدة والمتصفح بيـ Cache-ـه لكل باقي صفحات الموقع مجانًا. لو عملت Inline لكل الـ CSS جوه كل صفحة، بقيت بتبعت نفس الـ 12 KB دي من جديد في كل صفحة، من غير أي Caching. يعني "زوّد الـ HTML Bloat" ده بالظبط عكس اللي بيحصل في مواقع متعددة الصفحات.

يعني القاعدة الحقيقية مش "Tailwind صغير يبقى Inline كله دايمًا" — دي بتفرق حسب عدد الصفحات مش حجم الملف بس. لموقع بصفحة واحدة أو تطبيق SPA بشل واحد، الـ Inline الكامل غالبًا أبسط وأحسن. لموقع فيه عشرات الـ Routes زي Next.js، فقدان الـ Caching ده تكلفة حقيقية، ولسه له معنى تستخدم حاجة زي optimizeCss/inlineCss بتاعة Next نفسها بدل أدوات Critical CSS العامة.
