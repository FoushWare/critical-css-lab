🧠 مراجعة سريعة

Critical CSS بيكسبك إيه أصلًا؟

المتصفح مينفعش يرسم الصفحة قبل ما يحمّل ويحلّل ملفات الـ CSS المرتبطة بيها، يعني الـ CSS بيبقى Render-blocking. فكرة Critical CSS بسيطة: بدل ما نستنى كل الـ CSS، وندي المتصفح بس الجزء اللي محتاجه عشان يرسم أول حاجة ظاهرة — الـ Header والـ Hero — ونحطه مباشرة جوّه <style> في الـ <head>. ساعتها مفيش Network Request يوقف الرسم.

<!-- ده موجود جوّه الـ HTML نفسه، مفيش Request --> <head> <style> .hero { display: flex; background: #12151f; } </style> <!-- باقي الـ CSS يتحمّل عادي في الخلفية --> <link rel="stylesheet" href="main.css" > </head>

🔵 PIPELINE بتاع React CSR

طيب ليه نفس الحركة مش بتدي نفس النتيجة في React؟

لما تستخدم React بـ CSR — Client-Side Rendering — الـ HTML اللي السيرفر بيبعته الأول بيكون شبه فاضي:

<body> <div id="root"></div> </body>

مفيش Hero جاهز، مفيش Header جاهز، مفيش Content جاهز. مفيش حاجة تقريبًا يرسمها المتصفح 😅. لازم الأول JavaScript يوصل، وبعدين React يشتغل، وبعدين React يبني Virtual DOM — نسخة خفيفة في الميموري من شكل الصفحة — وبعدين يقارنها بالـ Real DOM (خطوة اسمها Reconciliation) عشان يعرف يحدّث إيه بالظبط، وبعد كل ده كله يجي دور الـ CSS.

⚠️
Critical CSS بيشيل بلوك واحد بس من الطريق. لكن في React CSR عندك أصلًا خطوات تانية كتير لازم تحصل قبل ما يبقى فيه حاجة تتترسم: تحميل الـ JS Bundle، تشغيله، React يعمل Render، بناء الـ Virtual DOM، الـ Diffing، وتحديث الـ Real DOM — وكل ده قبل ما الـ CSS يجيله دور أصلًا. يعني حتى لو قلت للـ CSS "اتفضل خد الـ Critical CSS ومتعطلش"، لسه قدامك JS Bundle → Render → Virtual DOM → Real DOM كلهم واقفين في الطابور. وده سبب الـ Diminishing Returns اللي شفته لما نقلت التجربة من Vanilla لـ React.
🧩 نقطة محتاجة توضيح

طب الـ Virtual DOM ده بيعمل إيه بالظبط؟

الـ Virtual DOM مش حاجة سحرية، هو مجرد نسخة JavaScript خفيفة من شكل الصفحة، React بيبنيها في الميموري (مش على الشاشة). كل مرة الـ State يتغيّر، React:

١

يبني Virtual DOM جديد

نسخة جديدة كاملة من شكل الصفحة المفروض تبقى عليه، لسه مش لمست الشاشة الحقيقية.

٢

يقارن (Diffing)

React يقارن النسخة الجديدة بالقديمة، ويحدد إيه اللي اتغيّر فعلًا — مش هيغيّر كل حاجة من الصفر.

٣

يحدّث الـ Real DOM

بس الفروقات اللي لقاها هي اللي بتتطبّق على الـ DOM الحقيقي — ده اللي بيخلي React سريع نسبيًا.

٤

بعدين يجي دور CSS والـ Paint

الشاشة متتلونش ولا تتترسم إلا بعد ما الخطوات التلاتة اللي فوق تخلص كلها.

يعني الـ Virtual DOM مش عبء زيادة من غير فايدة — هو اللي بيخلي React يقدر يحدّث صفحات معقدة بكفاءة. بس بالنسبة لأول Paint، هو خطوة إضافية قبل الـ CSS، مش بعده.

📋 عمليًا

طيب أستخدم Critical CSS إزاي في React؟

الفكرة لسه مفيدة، بس مكانها وأولويتها اتغيّروا. في Vanilla كنت بتحارب الـ CSS بس، أما في React CSR فأنت غالبًا بتحاول تتخطى JS Bundle + Render + Virtual DOM + CSS كلهم مع بعض.

يدويًا

Inline للـ App Shell

لو عندك Header أو Hero ثابتين، حط الـ HTML والـ CSS بتوعهم مباشرة في index.html، برّه الـ React root. المتصفح يرسمهم قبل ما JavaScript يبدأ أصلًا.

Tooling

@playform/critters

Fork متطور من Critters، بيشتغل كـ Post-build plugin: يبص على الـ HTML اللي اتعمله Render أو Prerender، ويطلع الـ CSS المستخدم فعلًا Inline، والباقي Lazy.

Framework

انقل من CSR لـ SSR / SSG

زي Next.js. أكبر نقلة ممكن تعملها — السيرفر يبعت HTML حقيقي، فالمتصفح يقدر يرسم قبل ما JS يشتغل بالكامل، وساعتها Critical CSS يرجع يبقى مؤثر تاني.

تجنّبه

Runtime CSS-in-JS في الـ Critical Path

زي styled-components وEmotion: الـ styles بتتولد أثناء الـ Render نفسه، يعني بتربط الـ CSS بالخطوة اللي أصلًا بتحاول تسبقها. لأول Paint، Plain CSS أو CSS Modules أبسط وأسرع.

🧠 الخلاصة

قبل ما تستخدم Critical CSS، اسأل نفسك ٣ أسئلة

الـ HTML اللي وصل حقيقي ولا فاضي؟١
إيه أكبر حاجة واقفة قبل الـ Paint؟٢
المشكلة فعلًا CSS؟٣

لو الإجابة "لا، المشكلة JavaScript"، يبقى متروحش تصلّح CSS — صلّح JavaScript الأول: قلّل حجم الـ Bundle، اعمل Code Splitting، استخدم Lazy Loading، انقل لـ SSR، أو قلّل شغل الـ Render نفسه. الحاجات دي هتعمل فرق أكبر بكتير من إنك تعمل Inline للـ CSS.

🎯
Critical CSS مش زرار Performance سحري. هو حل لمشكلة محددة: CSS هو اللي بيوقف الـ Paint. لو المشكلة عندك أصلًا JavaScript، فـ Critical CSS مش هيحل حاجة. باختصار: متصلّحش الـ CSS لو الـ JS هو اللي واقفلك الصفحة 😄
